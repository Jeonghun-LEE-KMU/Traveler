# CourseJSON 계약

CourseJSON은 LLM 코스 생성 결과와 백엔드·지도 UI 사이의 최소 데이터 계약이다.
런타임의 기준 구현은 `traveler.validation.schema.StreamingCourseModel`이다.

## 최상위 구조와 필드 순서

```json
{
  "bot_message": "사용자에게 먼저 보여줄 안내 문장",
  "recommended_places": [
    {
      "place_id": "17",
      "visit_sequence": 1,
      "place_name": "예시 장소",
      "duration_min": 60
    }
  ]
}
```

`bot_message`는 반드시 첫 번째 필드이고 `recommended_places`는 두 번째 필드다.
이 순서는 단순한 표현 규칙이 아니라, bot_message 텍스트를 먼저 스트리밍하고
장소 배열이 완성된 뒤 지도 핀을 갱신하기 위한 프론트엔드 계약이다.

## 장소 필드

- `place_id`: 필수 문자열이며 빈 문자열일 수 없다. content_id와 1:1로 연결된다
  (2026-08-09 변경: SQLite PK int는 DB 재구성 시 깨질 수 있어 문자열로 통일했다. Issue #15).
- `visit_sequence`: 필수 정수이며 1부터 시작한다.
- `place_name`: 선택 문자열이다. 없으면 백엔드가 place_id로 보강한다.
- `duration_min`: 선택 정수다. 없으면 백엔드 체류시간 데이터로 보강할 수 있다.

LLM의 `recommended_places`에는 장소가 1~10개 있어야 한다. 일반 추천은 3~5곳이며,
명시한 장소 수·시간 부족·후보 부족은 예외다. 서버는 시간 검증 결과가
`no_feasible`일 때만 빈 배열을 반환한다. 11개 이상은 스키마 검증 오류다.

## 서버의 예상 시간 검증 (PR47 후속)

`LLM 코스 → 좌표 기반 예상 이동 + 체류시간 검증 → 최종 코스 → 지도` 순서다.
`bot_message`, `recommended_places` 순서는 유지하고 세 번째 선택 필드
`time_budget`을 서버가 계산한다. LLM이 보낸 시간 요약은 신뢰하지 않고 다시 계산한다.

```json
{
  "budget_min": 240,
  "travel_min": 120,
  "stay_min": 90,
  "total_min": 210,
  "status": "within_budget",
  "note": "예상 총 210분(이동 120분 + 체류 90분) / 가용 240분",
  "method": "coordinate_estimate",
  "includes_initial_travel": true,
  "includes_return_travel": false
}
```

- 출발지→첫 장소와 장소 사이 이동을 합산하며, 마지막 장소에서 복귀하는 시간은 제외한다.
- 현재 추정은 좌표 직선거리 / 평균속도다. 자차 30km/h, 도보 4km/h이며 실제 도로·교통·주차는 반영하지 않는다.
- API는 전달된 `lat`, `lon`을 출발지로 보존한다. 지역 검색 중심점을 출발지로 대체하지 않는다.
- 체류시간이 없으면 관광·문화·음식 60분, 쇼핑 40분, 축제 90분, 기타 60분을 쓴다. 실측값이 아니다.
- `within_budget`: 예상 합계가 가용시간 이하. 실제 도착·종료 시각을 보장하지 않는다.
- `unverified`: 출발지·장소 좌표 또는 지원 가능한 이동 수단 정보가 부족하다. `travel_min`, `total_min`은 `null`이며 0분으로 취급하지 않는다.
- `no_feasible`: 추천할 수 있는 코스가 없어 빈 배열을 반환한다. 전역 최적 경로 탐색의 실패를 뜻하지 않는다.
- 가용시간이 장소 수보다 우선한다. 방문 순서를 유지하며 초과한 끝부분을 줄이고,
  가능한 실제 후보만 순서대로 보충한다. 최적 경로를 찾는 알고리즘은 아니다.
- `/api/chat/revise`에도 같은 검증을 적용하지만 삭제한 장소를 최소 3곳 규칙으로 다시 채우지 않는다.
- 가용시간은 정수 분으로 통일한다. `30분`→30, `1.5시간`→90,
  `4시간 30분`→270, `1시간 반`→90분이다. 범위는 1~720분이다.
  0·음수·720분 초과·분 미만 정밀도·`3~5시간` 같은 범위는 안내 오류를 반환한다.
  `1시간 이내 거리`, `30분 걸리는 곳`, `하루 전에 예약`은 가용시간으로 읽지 않는다.
  미지정 새 추천은 기존 3~5시간 기본값(상한 300분), 미지정 수정은 저장된 예산을 유지한다.
- `총 2곳으로 줄여줘` 같은 전체 수 지정만 총량 제한이다. `카페 1곳 추가`,
  `총 2곳만 빼줘`, `맛집 2곳 포함`의 수를 전체 코스 수로 쓰지 않는다.
  수정 결과는 시간 내에서 최대 10곳까지 보존하며 최소 3곳을 다시 채우지 않는다.
- 기차·열차·KTX·SRT·대중교통 및 혼합·불명 수단은 `unverified`다.
  이동수단 미지정으로 자차를 가정해 계산했다면 `note`에 가정 사실을 적는다.
  `transport_assumed`는 내부 문맥 필드이며 wire `time_budget`의 필드가 아니다.
- API 장소의 `lat`, `lng`는 후보 ID에 연결된 좌표만 사용한다. 누락·0·비유한·범위 밖이면
  두 값 모두 `null`이다. 출발지 GPS만 없는 경우에는 유효한 장소 좌표를 지우지 않는다.

SSE 중간 청크의 `recommended_places: []`는 이전과 같다. 최종 청크는
`time_budget`과 확정 장소 목록, `bot_message`의 추가 예상 일정 안내를 담는다.
프론트는 `time_budget`이 있는 최종 청크의 빈 장소 목록도 최종 결과로 처리해야 한다.
LLM 문장은 검증 전에 스트리밍된다. 최종 안내는 앞선 문장이 검증 전 제안임을 알리며,
지도와 장소 카드는 마지막 검증 결과를 기준으로 표시해야 한다.

### 오류와 종료 구분

`GET /api/chat`은 자연어 입력 오류 또는 생성/준비 실패를 HTTP 200 SSE 안에서
별도의 이름 있는 이벤트로 보낸다. EventSource의 연결 오류와 구분하기 위한 계약이다.

```text
event: application_error
data: {"error":{"code":"INVALID_REQUEST","message":"가용 시간은 1분 이상 12시간 이하의 정수 분으로 입력해 주세요.","retryable":false}}

```

생성 실패는 `GENERATION_FAILED`, `retryable: true`이다. 내부 예외·키·주소는
안내에 넣지 않는다. 오류에 `time_budget`을 붙여 정상 최종 결과로 위장하지 않는다.
라우트 진입 전 필수 쿼리/숫자 형식 검증은 FastAPI의 HTTP 오류로 남는다.
`POST /api/chat/revise`는 잘못된 가용시간에 422 + `detail`, 저장 코스 없음에
404 + `detail`을 반환한다. 422는 이전 코스를 바꾸지 않는다.

다음은 프론트 담당자와의 연동 요구사항이며, 이번 PR에서 프론트 구현을 변경한 것은 아니다.
프론트는 non-null `time_budget`으로 정상 최종 결과를 식별하고, 빈 배열도 반영한다.
정상/오류 이벤트를 처리한 뒤 EventSource를 닫고 후속 `onerror`를 무시한다.
최종 이벤트 전 끊김은 별도 연결 오류다. 빈 최종 결과는 이전 카드·핀·경로·상세 캐시와
서버 저장 코스를 비우며, 다음 입력은 새 추천으로 요청한다.
빈 결과 이후 재요청의 목적지 전달과 입력 UI는 프론트 담당자와 별도로 연동한다.
이번 정훈 담당 변경에서는 빈 코스 전용 목적지 보존 기능을 추가하지 않는다.

실제 직렬화 함수를 사용해 만든 [로컬 응답 샘플](fixtures/final_response_samples.json)과
[PM 검증 절차](PR47_PM_HANDOFF.md)를 함께 참고한다. 샘플은 실제 LLM 결과가 아니다.

## 정규화와 검증

- `duration_min`이 있으면 10~480분 범위로 clamp한다. 예를 들어 5는 10으로,
  600은 480으로 정규화한다.
- 장소 배열은 `visit_sequence` 기준으로 정렬한다.
- 정렬 후 순서는 1, 2, 3처럼 연속이어야 한다. 중복 또는 누락된 순번은
  검증 오류다.
- `place_name`이 제공됐다면 공백 문자열일 수 없다.

## 실패와 fallback

LLM 응답이 JSON 파싱에 실패하거나 위 스키마를 통과하지 못하거나 API 호출이
실패하면 코스 생성기는 예외를 사용자에게 전파하지 않고 fallback
`StreamingCourseModel`을 반환한다. 후보 장소가 있으면 실제 후보를 대상으로
시간 검증을 적용한다. 후보가 없으면 가짜 ID 대신 빈 장소 배열과 `no_feasible`을 반환한다. 이 동작은
서비스 중단을 피하기 위한 Graceful Degradation이며, 잘못된 원본 응답을
정상 데이터로 간주한다는 뜻은 아니다.

## LLM, 백엔드, 지도 enrichment 경계

LLM의 책임은 후보 목록에 grounding된 `place_id`, 방문 순서, 사용자용 문장을
생성하는 것이다. 좌표를 만들거나 존재하지 않는 장소 ID를 추측하지 않는다.

백엔드는 place_id를 기준으로 SQLite/TourAPI에서 `place_name`, 위도·경도,
필요한 경우 `duration_min`을 enrichment한다. 지도/프론트엔드는 백엔드가
검증하고 보강한 좌표와 장소 정보를 표시하며, LLM 원문을 좌표 데이터로 직접
사용하지 않는다. 이 경계는 장소명·좌표 환각이 지도 핀으로 전파되는 것을 막는다.
