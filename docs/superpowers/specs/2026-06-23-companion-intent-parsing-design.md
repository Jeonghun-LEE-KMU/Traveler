# Companion Intent Parsing — 설계 spec

- 작성일: 2026-06-23
- 프로젝트: 트래블러 (mobility_rag) — 한이음 드림업 공모전 LLM 파이프라인
- 담당: 이정훈 (LLM 엔지니어)
- 단계: 설계(브레인스토밍) — **이 spec은 사용자 승인 전이며, 승인 전까지 구현 코드를 작성하지 않는다.**

---

## 1. 개요 (Problem / Goal)

### 문제
`traveler/rag/retriever.py`의 `get_context()`(현재 DUMMY 상태)가 동승자 유형을
`companion="친구"`로 **하드코딩**하고 있다(retriever.py:77). 사용자가 실제로 누구와
여행하는지와 무관하게 항상 "친구"가 GPT 프롬프트에 주입된다.

### 목표
사용자 자연어 입력(`user_query`)에서 **동승자 유형(companion)을 규칙 기반으로 추출**하는
순수 함수를 만들고, `get_context()`가 이 함수를 호출하도록 한다.

### 비목표 (Non-goals)
- **LLM 호출 없음.** 100% 규칙(키워드 매칭) 기반이다. (비용 0, 지연 0)
- **mood(분위기)는 다루지 않는다.** `ContextData.mood` 필드 주석이
  "분위기 힌트 (Pinecone 쿼리에서 추출)"라서 이수연의 Sprint 3 Pinecone
  파이프라인 책임 영역이다. (결정 1)
- `types.py`(인터페이스 계약)는 수정하지 않는다. (결정 5)

## 2. 아키텍처 / 배치 결정

### 2.1 새 모듈 위치 — `traveler/core/intent.py` (결정 2)

순수 함수 모듈로 `traveler/core/intent.py`를 신설한다. `season.py`와 같은
`core/` 계층(외부 의존 없는 순수 함수)에 둔다.

**호출 지점은 `retriever.py`의 `get_context()` 한 곳이다. `prompt.py`에서 호출하지
않는다.** 이유:

- `user_query`는 이미 `ContextData`의 필드다(types.py:50). `prompt.py`가 독자적으로
  `user_query`에서 companion을 다시 추출하면 `ContextData.companion`(retriever가 채운 값)과
  **이중 소스(dual source of truth)** 충돌이 발생한다.
- 반면 `season.py`는 입력이 "오늘 날짜"라서 `ContextData` 외부 값이다. 그래서
  `prompt.py`가 직접 호출해도 이중 소스 문제가 없다 — **다른 패턴이며, 이 차이가 배치를
  가르는 핵심 근거다.**

```
사용자 입력(user_query)
   │
   ▼
get_context()  ← intent.parse_companion(user_query) 호출
   │            (companion 필드를 하드코딩 대신 추출값으로 채움)
   ▼
ContextData(companion=...)
   │
   ▼
build_context_message()  ← ctx.companion을 읽기만 함 (재추출 안 함)
   │
   ▼
GPT-4o
```

### 2.2 fallback 값 — 빈 문자열 `""`, 단 "혼자" 명시는 `"혼자"` (결정 3 — 개정)

**핵심 구분**: "동승자를 아예 언급하지 않은 것"과 "혼자라고 명확히 말한 것"을 구분한다.

| 상황 | 반환 | 의미 |
|---|---|---|
| 어떤 카테고리도 매칭 안 됨 (동승자 미언급) | `""` | "정보 없음" — 동행자 줄을 프롬프트에서 뺀다 |
| 명시적으로 "혼자"/"혼행"/"나홀로" 등 언급 | `"혼자"` | "혼자 여행한다"는 실제 정보 — GPT에 전달한다 |

- `"명시안함"` 같은 sentinel 문자열은 쓰지 않는다. 미언급은 빈 문자열 `""` 하나로만 표현한다.
- **개정 사유**: 종전에는 "혼자" 매칭도 `""`로 통일했다(어떤 sentinel이든 `prompt.py:326`의
  `f"동행자: {ctx.companion}"`에 주입되어 GPT에 솔로 편향을 줄 수 있다는 우려). 그러나
  **사용자가 실제로 "혼자 간다"고 명시했다면 그 정보를 GPT에 전달하는 것은 편향이 아니라
  정확한 정보 전달**이다. 편향 우려는 "미언급을 솔로로 단정"할 때만 성립한다 — 미언급은
  여전히 `""`로 막으므로 그 우려는 해소된 채로 남는다.
- 미언급(`""`)일 때는 결정 4의 `if ctx.companion:` 가드와 결합해 해당 줄 자체가 프롬프트에서
  빠진다. 반면 `"혼자"`는 비어있지 않은 문자열이라 가드를 **통과**하여 `"동행자: 혼자"`로
  GPT에 주입된다(결정 4·2.3 참조).

### 2.3 구현 단계에서 함께 적용할 변경 (이 spec은 설계만 — 코드 미작성)

- **`prompt.py:326`** — `parts.append(f"동행자: {ctx.companion}")`를
  `if ctx.companion:` 가드로 감싼다. 기존 mood/route_summary 패턴(prompt.py:330-333)과 동일.
  (결정 4)
  - 이 가드는 **빈 문자열만** 걸러낸다. 따라서 미언급(`""`)이면 "동행자" 줄이 빠지고,
    `"혼자"`/`"연인"` 등 **비어있지 않은 라벨은 그대로 통과**하여 `"동행자: 혼자"`처럼
    주입된다. 즉 2.2의 개정으로 "혼자"가 진짜 문자열이 되면서, 별도 코드 변경 없이 이
    가드를 자연히 통과해 GPT에 전달된다(가드 로직 자체는 손댈 필요 없음).
- **`retriever.py:77`** — `companion="친구"` 하드코딩을
  `companion=parse_companion(user_query)`로 교체한다. (결정 2)
- **`types.py`는 건드리지 않는다.** `ContextData.companion: str = "혼자"` 기본값
  그대로 둔다 (types.py:59). 실제로는 retriever가 항상 명시적 값을 넘기므로 이 기본값은
  거의 안 쓰인다. (결정 5)
  - **개정에 따른 주의(소거 가능한 위험)**: 이번 정책 개정으로 `"혼자"`가 "솔로 여행"을
    뜻하는 의미 있는 라벨이 됐다. 그래서 만약 retriever가 값을 안 넘겨 이 기본값이
    노출되면, 미언급인데도 "동행자: 혼자"가 GPT에 주입되는 — 새 정책이 피하려던 "미언급을
    솔로로 단정" — 상황이 된다. 현재는 retriever가 항상 명시적으로 채우므로 실제로는
    발생하지 않는다(6.8 통합 테스트가 이 경로를 고정). `types.py` 무수정 원칙은 유지하되,
    이 위험은 알고 있는 것으로 기록한다(향후 기본값을 `""`로 바꾸는 건 결정 5 재논의 대상).

## 3. 컴포넌트 — 모듈 인터페이스 (설계 항목 A)

### 3.1 함수 시그니처

```python
def parse_companion(user_query: str | None) -> str:
    ...
```

- **입력**: `user_query: str | None` — 사용자 자연어 요청. `None`/빈/공백 입력도 허용
  (4절 에러 처리 참조).
- **출력**: `str` — 동승자 유형 라벨(예: `"연인"`, `"가족"`, `"혼자"`) 또는 빈 문자열 `""`(매칭
  실패 / 빈 입력 = **동승자 미언급**). `"혼자"`는 사용자가 명시적으로 혼자 여행을 언급한
  경우의 실제 라벨이며 빈 문자열이 아니다(2.2 참조).
- **함수 이름 근거**: `parse_*` 접두사로 "원시 텍스트 → 구조화된 라벨" 변환임을 드러낸다.
  모듈명 `intent.py`는 향후 동승자 외 의도(intent) 추출이 추가될 여지를 남기되, 이번
  스코프는 companion 단일 함수다(과설계 금지 — 지금은 함수 하나만).

### 3.2 키워드 표 자료구조 — `dict[str, list[str]]`

키워드 표는 **모듈 레벨 상수**로 둔다. 매핑은 삽입 순서가 곧 우선순위이므로
(결정 7), Python 3.7+ dict의 삽입 순서 보장에 의존한다.

```python
_COMPANION_KEYWORDS: dict[str, list[str]] = {
    "연인":        [...],
    "배우자":      [...],
    "아이":        [...],
    "부모님 모시고": [...],
    "가족":        [...],
    "반려동물":     [...],
    "단체/모임":    [...],
    "친구":        [...],
    "혼자":        [...],   # 매칭 시 라벨 "혼자" 반환 (3.4 참조)
}
```

- **키(key)** = 출력 라벨, **값(value)** = 부분 문자열 매칭에 쓸 키워드 리스트.
- 모듈 레벨 상수로 두는 이유: import 시 한 번만 생성(module-level 로딩). 함수 호출마다
  dict를 재생성하지 않아 불필요한 할당을 피한다. 또한 표를 함수 밖에 두면 테스트에서
  표 자체를 직접 검증할 수 있다.

### 3.4 우선순위 (결정 7 — 확정)

표의 **위에서부터 순서대로** 검사하고 **첫 매칭에서 멈춘다(short-circuit)**:

```
연인 → 배우자 → 아이 → 부모님 모시고 → 가족 → 반려동물 → 단체/모임 → 친구 → 혼자(→ "혼자")
```

- 더 구체적인 카테고리("아이", "부모님 모시고")를 일반적인 "가족"보다 **위**에 둔 이유:
  "가족이랑 아이 데리고" 같은 입력에서 더 구체적인 "아이"가 이기게 하기 위함.
- **"혼자" 카테고리는 매칭되면 라벨 `"혼자"`를 반환한다(개정).** 사용자가 명시적으로
  "혼자"/"혼행"/"나홀로" 등을 말한 경우이므로, 이를 실제 정보로 GPT에 전달한다(2.2 참조).
  매칭 실패(미언급)는 여전히 `""`이며, 이 둘은 **이제 구별된다**.
- **"혼자"를 우선순위 맨 아래(8번째, 친구 다음)에 둔 위치는 그대로 유지한다.** 근거:
  "혼자"는 가장 약한 신호다. 다른 동승자 카테고리가 하나라도 매칭되면 사용자가 누군가와
  함께 간다는 더 강한 정보가 있는 것이므로 그쪽이 이겨야 한다. 예컨대 "혼자 운전해서 친구
  만나러"처럼 "혼자"와 "친구"가 함께 나오면 동행 정보인 "친구"가 우선이다. 따라서 "혼자"는
  **다른 모든 동승자 카테고리가 전부 안 잡혔을 때만** 최종적으로 잡히는 위치가 맞다.
  (라벨이 `""`에서 `"혼자"`로 바뀌었을 뿐, 순서를 바꿀 이유는 없다.)

### 3.5 매칭 방식 (결정 8 — 확정)

정규식 단어경계(word-boundary)가 아니라 **단순 Python `in` 부분 문자열 매칭**을 쓴다.

```python
if keyword in user_query:   # 부분 문자열 매칭
```

- 이유: 한국어는 어절 경계가 모호해 정규식 word-boundary 효과가 제한적이라 과설계로
  판단했다.
- 부작용(예: "남친"이 "남친구" 안에서 우연히 매칭)은 **9절 Known Limitations**에 명시하고,
  **회귀 테스트로 그 동작을 고정(pin)**한다. 아키텍처로 막지 않는다.

### 3.6 순수 함수 보장 방법 (설계 항목 A)

`parse_companion`이 순수 함수(pure function)임을 다음으로 보장한다:

- **부작용 없음**: I/O(파일/네트워크/DB) 없음, 전역 상태 변경 없음, 로깅 없음.
- **결정성**: 같은 입력 → 항상 같은 출력. `date.today()` 같은 wall-clock 의존 없음
  (season.py와 달리 시간 입력 자체가 없다).
- **읽기 전용 상수 참조**: `_COMPANION_KEYWORDS`를 **읽기만** 하고 수정하지 않는다.
- 이 순수성 덕분에 테스트가 고정 입력만으로 전 동작을 검증할 수 있다(season.py의
  `today` 주입 패턴과 같은 철학).

## 4. 에러 / 예외 처리 (설계 항목 B)

**원칙: Graceful Degradation — 예외를 던지지 않고 빈 문자열로 안전하게 퇴화한다.**

`user_query`가 비정상일 때의 처리:

| 입력 | 처리 | 반환 |
|---|---|---|
| `None` | 매칭 시도 없이 즉시 반환 | `""` |
| `""` (빈 문자열) | 어떤 키워드도 `in ""` 매칭 불가 | `""` |
| `"   "` (공백뿐) | 어떤 키워드도 매칭 불가 (필요 시 `.strip()`으로 명시 처리) | `""` |
| 매칭 실패(키워드 없음 = 미언급) | 표 끝까지 못 찾음 | `""` |
| "혼자" 매칭 | 3.4 참조 — 라벨 반환 | `"혼자"` |

- **`None` 가드를 먼저 둔다.** `"keyword" in None`은 `TypeError`를 던지므로, 함수
  진입부에서 `if not user_query: return ""`로 `None`과 빈 문자열을 한 번에 막는다.
  (공백뿐인 문자열은 `not "   "`가 `False`라 이 가드를 통과하지만, 어차피 어떤 키워드도
  매칭되지 않아 자연히 `""`로 떨어진다 — 별도 `.strip()`은 선택이며 가독성 목적.)
- **예외를 던지지 않는 이유**: 이 함수는 파이프라인 중간 단계다. 입력이 이상하다고
  파이프라인 전체를 멈추면 안 된다(데이터 없어도 동작하는 설계). 빈 문자열을 반환하면
  결정 4의 `prompt.py` 가드와 결합해 "동행자" 줄이 프롬프트에서 빠질 뿐, GPT는 정상
  동작한다.

### 4.1 retriever.py 호출 지점 추가 처리

`retriever.py`의 `get_context()`에서 `companion=parse_companion(user_query)`로 호출할 때
**추가 처리는 불필요하다.**

- `user_query`는 `get_context`의 파라미터이고 기본값이 있는 `str`이라, 호출 시 항상
  문자열이 넘어온다.
- 설령 호출자가 `None`을 넘겨도 `parse_companion` 내부 `None` 가드가 흡수한다.
- 즉 retriever 쪽에는 try/except나 None 체크를 넣지 않는다(중복 방어 금지, 책임 분리).

## 5. 데이터 흐름 (요약)

```
1. 사용자가 user_query 입력
2. get_context(user_query)가 parse_companion(user_query) 호출
3. parse_companion이 _COMPANION_KEYWORDS를 우선순위 순으로 검사
     - 첫 매칭 라벨 반환 ("혼자" 매칭이면 "혼자")
     - 매칭 실패(미언급)/입력 실패 시 "" 반환
4. 반환값을 ContextData(companion=...)에 저장
5. build_context_message()가 ctx.companion을 읽음
     - 빈 문자열(미언급)이면 (prompt.py 가드) "동행자" 줄 생략
     - 값이 있으면 "동행자: {라벨}" 줄 주입 ("혼자"도 여기에 포함 → "동행자: 혼자")
6. GPT-4o 호출
```

## 6. 테스트 전략 (설계 항목 C)

테스트는 **세 곳**에 걸쳐 둔다. 단위(parse 함수) → 통합(retriever가 값을 채움) →
프롬프트(가드가 값을 올바르게 출력) 순서로 책임을 분리해 검증한다.

| 파일 | 검증 대상 | 비고 |
|---|---|---|
| `tests/test_intent.py` (신규) | `parse_companion` 단위 동작 (6.1~6.7) | 순수 함수, 일반 `def test_*` |
| `tests/test_retriever.py` (신규) | `get_context()`가 parse 결과를 `companion`에 채움 (6.8) | 통합 |
| `tests/test_course_generator.py` (기존) | `if ctx.companion:` 가드의 출력/생략 (6.9) | 프롬프트 |

**6.1~6.7은 새 파일 `tests/test_intent.py`.** 기존 `tests/test_season.py` 스타일을 따른다
(순수 함수, 고정 입력, docstring으로 WHY 설명, 평이한 `assert`). 비동기 아님(일반
`def test_*`).

### 6.1 카테고리별 매칭 (각 1건 이상)

"혼자"를 제외한 동승자 카테고리 8개를 각각 대표 입력 1건으로 검증한다("혼자"는 라벨을
반환하지만 정책상 별도 케이스라 6.4에서 다룬다):

| 테스트 | 입력 예시 | 기대 출력 |
|---|---|---|
| 연인 | "여자친구랑 부산 데이트 코스 추천" | "연인" |
| 배우자 | "와이프랑 제주 신혼여행" | "배우자" |
| 아이 | "아이들 데리고 갈 만한 곳" | "아이" |
| 부모님 모시고 | "부모님 모시고 효도여행 가고 싶어요" | "부모님 모시고" |
| 가족 | "온가족 나들이 코스" | "가족" |
| 반려동물 | "강아지랑 갈 수 있는 곳" | "반려동물" |
| 단체/모임 | "회사 워크샵 장소" | "단체/모임" |
| 친구 | "친구들이랑 놀러 갈 곳" | "친구" |

### 6.2 다중 매칭 우선순위 (결정 7 검증)

- `"가족이랑 아이 데리고 갈 곳"` → `"아이"`
  ("가족"과 "아이" 둘 다 매칭되지만 "아이"가 표에서 위라 이긴다)
- `"부부 동반 부모님 모시고 여행"` → `"배우자"`
  ("배우자"가 "부모님 모시고"보다 위 — 우선순위 순서를 명시적으로 고정)
- `"친구랑 강아지 데려가도 되나요"` → `"반려동물"`
  ("반려동물"이 "친구"보다 위)

### 6.3 부분 문자열 오탐 (결정 8 — 알려진 한계를 테스트로 pin)

- `"남친구랑 여행"` → `"연인"`
  ("남친"이 "남친구" 안에서 매칭되는 오탐. **버그가 아니라 의도된 알려진 한계**임을
  테스트로 명시 고정한다. 이 동작이 우연히 바뀌면 테스트가 깨지며 "한계가 변했다"를
  알린다.)

### 6.4 "혼자" 명시 시 라벨 `"혼자"` 반환 (결정 3 개정·7)

- `"혼자 훌쩍 떠나고 싶어요"` → `"혼자"`
- `"나홀로 여행 코스"` → `"혼자"`
  (명시적으로 "혼자"라고 말한 경우이므로 실제 정보로 GPT에 전달. 미언급과 구별된다 —
  6.5의 미언급 케이스가 `""`인 것과 대비.)

### 6.5 동승자 미언급 시 빈 문자열 (6.4와 대비)

- `"맛집 추천해줘"` → `""` (어떤 동승자 키워드도 없음 = 미언급)
- `"경주에서 반나절 자차로 여행하고 싶어요"` → `""`
  (retriever.py의 현재 더미 기본 user_query — 동승자 언급 없음 → 빈 문자열)

> **6.4 vs 6.5가 핵심 대비**: "혼자"라고 명시하면 `"혼자"`(6.4), 동승자를 아예 언급
> 안 하면 `""`(6.5). 이 두 케이스를 같은 테스트 파일에 나란히 둬서 정책의 의도("명시한
> 혼자"와 "미언급"의 구별)를 회귀로 고정한다.

### 6.6 None / 빈 입력 (4절)

- `parse_companion(None)` → `""` (TypeError 안 남)
- `parse_companion("")` → `""`
- `parse_companion("   ")` → `""`

### 6.7 (선택) 표 정합성 메타 테스트

- `_COMPANION_KEYWORDS`의 키 순서가 결정 7의 우선순위와 일치하는지 검증하는 테스트를
  둘 수 있다(표를 나중에 누가 재정렬하면 깨지게). 과해 보이면 생략 가능 — 6.2가 이미
  순서를 간접 검증한다.

### 6.8 `get_context()`가 parse 결과를 `companion`에 채우는지 (통합 — 신규 파일)

새 파일 `tests/test_retriever.py`. `get_context()`가 더 이상 `companion="친구"`로
하드코딩하지 않고 `parse_companion(user_query)`의 반환값을 그대로 `ContextData.companion`에
채우는지 검증한다. parse 함수 단위 테스트(6.1~6.7)와 별개로, **두 모듈이 실제로 연결됐는지**를
보장하는 통합 지점이다(하드코딩 회귀를 막는다).

| 테스트명 | 입력 user_query | 기대 `ctx.companion` |
|---|---|---|
| `test_get_context_fills_companion_from_query` | "여자친구랑 부산 데이트" | "연인" |
| `test_get_context_solo_query_fills_honja` | "혼자 훌쩍 떠나고 싶어요" | "혼자" |
| `test_get_context_no_companion_fills_empty` | "맛집 추천해줘" | "" |

- `get_context()`가 비동기(`async def`)이면 테스트도 `async def`로 두고 `await`한다.
  Pinecone/외부 I/O를 호출하는 부분이 있으면 해당 의존만 mock하고, **검증의 초점은
  `companion` 필드값** 한 가지로 좁힌다(테스트 1개 = 검증 1개).
- "혼자"/"미언급" 두 케이스(2·3행)를 함께 둬서 6.4↔6.5의 정책 구분이 retriever 통합
  레벨에서도 유지되는지 확인한다.

### 6.9 `if ctx.companion:` 가드의 출력/생략 (프롬프트 — 기존 파일)

기존 파일 `tests/test_course_generator.py`에 추가한다. 결정 4의 가드가 `build_context_message()`
출력에 올바르게 반영되는지 — companion이 있으면 "동행자:" 줄이 **포함**되고, 빈 문자열이면
**생략**되는지 — 를 검증한다. mood/route_summary를 검증하는 기존 `test_optional_fields_included_only_when_set`(Test 4)과 같은 패턴이다.

| 테스트명 | ctx.companion | 기대 |
|---|---|---|
| `test_companion_line_included_when_set` | "혼자" | `"동행자: 혼자"`(또는 `"동행자"` + `"혼자"`)가 메시지에 **포함** |
| `test_companion_line_omitted_when_empty` | "" | `"동행자"`가 메시지에 **없음** |

- 두 테스트 모두 동기 `def test_*` (build_context_message는 동기 함수). `minimal_ctx(companion=...)`
  픽스처를 재사용한다.
- 포함 케이스는 "혼자"를 쓴다 — 개정된 정책에서 "혼자"가 빈 문자열이 아니라 가드를
  통과하는 실제 라벨임을 이 테스트가 직접 고정한다(2.2·결정 4 검증).

### 6.10 기존 `test_required_fields_included` 수정 (정책 변경 반영 — 기존 파일)

`tests/test_course_generator.py`의 기존 **Test 1 `test_required_fields_included`**(현재
파일 line 87~107)는 `companion="혼자"`를 넣고 `assert "혼자" in msg`로 검증한다. 종전
정책(혼자→"")에서는 이 기대값이 **잘못된 것**이었으나(혼자가 빈 문자열이라 메시지에서
빠졌어야 함), **개정된 정책에서는 "혼자"가 실제로 메시지에 들어가므로 이 단언이 비로소
올바르게 통과한다.**

- **기대값 변경 불필요**: 기존 `assert "혼자" in msg`는 개정 정책과 정확히 일치한다.
  (종전 정책이 실제 코드로 구현됐다면 이 테스트는 실패했을 것 — 즉 spec과 테스트가
  어긋나 있었다. 개정으로 정합성이 맞춰진다.)
- **이름/의도 정비(권장)**: 이 테스트는 "필수 필드 5종 포함"과 "혼자=실제 라벨"이라는
  두 관심사를 섞고 있다. companion 관련 단언만 떼어 6.9의 `test_companion_line_included_when_set`로
  옮기는 것을 권장한다. 다만 기존 테스트를 그대로 둬도 개정 정책과 모순되지 않으므로,
  **분리는 선택**이고 최소한 기대값은 손대지 않는다(서지컬 변경 원칙).

## 9. Known Limitations (알려진 한계)

1. **부분 문자열 오탐**: `in` 매칭이라 키워드가 더 긴 단어 안에 우연히 포함되면 오탐이
   난다(예: "남친" ⊂ "남친구" → "연인"). 의도된 트레이드오프이며 6.3 테스트로 동작을
   고정한다. 추후 오탐이 실사용에서 문제가 되면 해당 키워드만 더 길게 바꾸거나 표에서
   제거하는 식으로 대응한다(아키텍처 변경 아님).
2. **다중 동승자 표현 손실**: "친구랑 가족이랑"처럼 둘 이상을 진짜로 동반하는 경우에도
   우선순위상 하나의 라벨만 반환한다. 단일 라벨 모델이 현 스코프의 의도다.
3. ~~**"혼자" 정보 소실**~~ → **해결됨 (결정 3 개정)**: 종전에는 "혼자" 명시도 빈
   문자열로 처리해 정보가 소실됐으나, 개정으로 "혼자" 명시 시 라벨 `"혼자"`를 반환해
   GPT에 전달한다. 단, **동승자 미언급**은 여전히 `""`로 두어 "솔로로 단정"하지 않는다 —
   즉 "명시한 혼자"만 정보로 살리고, "아무 말 안 한 것"은 정보 없음으로 둔다. (남은 미세
   한계: "혼자" 키워드가 사전에 없는 표현으로 솔로를 암시하면(예: "나 빼고 아무도 없이")
   못 잡는다 — 이는 한계 4 "고정 키워드 사전"의 일부다.)
4. **고정 키워드 사전**: 신조어/오타/방언/외국어 표현은 사전에 없으면 못 잡는다. LLM이
   아니라 규칙 기반이라는 본질적 한계이며, 비용 0·지연 0·결정성이라는 이점과의 트레이드오프다.
5. **mood 미처리**: 분위기 추출은 이수연의 Pinecone 파이프라인(Sprint 3) 소관이라 이
   기능에서 다루지 않는다(스코프 밖).
